# 前后端一体项目开发规范

## 使用原则

- 先阅读当前项目的需求文档、设计稿、接口文档、现有代码和项目级 skill，再做实现判断。
- 默认使用中文沟通；代码、命令、包名、接口名、环境变量保持英文原文。
- 优先复用项目现有框架、目录结构、样式变量、组件模式、接口封装和错误处理方式。
- 改动范围保持克制，只解决当前目标，不顺手做无关重构。
- 前端可见交互、路由、动画、菜单、表单、下载、搜索、拖拽等改动完成后，优先用 Playwright 做真实浏览器验证。
- 如果项目已有明确规范，以项目规范优先；本 skill 作为默认工程和体验基线。

## 推荐技术栈

### 前端

- 使用 Next.js + TypeScript + React。
- 使用 Ant Design 作为后台管理和表单控件基础，但视觉层不要被 AntD 默认样式牵着走，要按项目设计规范做统一外观。
- 使用 React Query 管理服务端状态，缓存 key 必须显式包含影响数据的上下文，例如 `repoId`、`branch`、`path`、`page`、`keyword`。
- 使用全局 API 封装处理 token、错误消息、JSON 解析、下载地址和公共响应类型。
- 使用 CSS 或 CSS Modules 管理项目样式，优先沉淀稳定 class，避免大量不可维护的内联样式。

### 后端

- 使用 NestJS + TypeScript。
- 业务能力按模块拆分：认证、用户、配置、资源管理、搜索、导出、系统设置等。
- 控制器只负责 HTTP 入参、权限和响应；核心逻辑收敛到 Service。
- 所有外部系统调用，例如 Git、搜索引擎、数据库、文件系统、浏览器导出，都要有统一入口，集中处理锁、重试、错误、日志和状态。
- DTO 和接口类型要清晰，前后端共享契约时优先同步更新 API 文档。

### 基础设施

- 使用 npm workspace 管理前后端目录，例如根目录包含 `frontend` 和 `backend`。
- 使用 Docker Compose 组织前端、后端、数据库、搜索服务、Nginx 等基础服务。
- 使用 Nginx 提供统一入口，前端访问后端统一走 `/api` 前缀。
- 提供根目录脚本：
  - `restart.sh`：一键启动或重启。
  - `stop.sh`：一键停止。
  - 必要时提供 Docker 镜像源、初始化、迁移或健康检查脚本。
- 生产配置通过环境变量注入，禁止把密码、token、私钥、内部地址写死进代码。

## 项目结构规范

- 根目录保留 `README.md`、`.env.example`、`docker-compose.yml`、启动/停止脚本和关键文档。
- `frontend/src/app` 放页面和路由入口。
- `frontend/src/components` 放可复用组件、图标、认证 hook、布局组件。
- `frontend/src/lib` 放 API、工具函数、类型和跨页面复用逻辑。
- `backend/src/<module>` 按业务模块组织 Controller、Service、DTO、Guard、Store。
- `docs/` 放需求、接口、UI、部署、性能、排查和设计决策文档。
- 静态目录即使为空也要保留占位文件，例如 `public/.gitkeep`，避免 Docker 构建时目录缺失。

## 前后端契约规范

- 所有接口统一前缀，例如 `/api`。
- 请求和响应默认 JSON；文件下载使用二进制流，并正确设置 `Content-Disposition`，中文文件名使用 `filename*=UTF-8''...`。
- 前端 API 封装要把后端错误转换成用户可读消息。
- 接口失败不得静默；页面必须通过 message、inline error、tooltip 或状态区域展示失败原因。
- 状态类接口要返回明确状态，例如 `idle | queued | running | success | failed`。
- 重任务不要同步阻塞页面请求；创建任务后返回任务 ID，前端轮询状态并提供下载、重试或错误说明。
- 查询类接口必须显式携带完整上下文参数，避免依赖服务端全局状态。
- 权限失败、登录过期、资源不存在、参数错误、外部服务失败要返回可区分的 HTTP 状态和摘要消息。

## 状态与性能规范

- 前端阅读/筛选/切换上下文应同步到 URL 或路由状态，刷新页面后不应闪烁错误默认值。
- 不要在数据尚未加载时展示假默认值；使用空值、骨架屏、渐入动画或占位状态。
- 切换仓库、分支、租户、项目、环境等上下文时，只改变当前阅读/操作上下文，不应修改服务端全局状态。
- 后端缓存 key 必须包含所有影响结果的维度，例如 `resourceId + version + path`。
- 重操作必须做并发控制：
  - 同一上下文只允许一个运行中的任务。
  - 已有任务运行时复用状态。
  - 设置最小刷新间隔，避免页面加载风暴。
- 搜索索引、树形数据、导出结果、渲染结果要绑定版本号或 commit/hash，避免缓存串数据。
- 删除或重新配置资源时，必须清理相关缓存、索引、临时文件和任务状态。

## 通用 UI 设计规范

- 默认采用浅色后台风格，但整体要“文档优先、纯白、沉浸式、少干扰”。
- 背景优先使用纯白 `#ffffff`。
- 弱化大卡片、大边框和明显外边距；只在需要分组时使用浅灰背景或轻阴影。
- 视觉层级靠字号、字重、留白、浅灰背景和状态色建立，不靠大量颜色堆叠。
- 主色默认使用商务绿 `#198754`；除主操作和高亮外，不要滥用主色。
- 灰色系统要统一：
  - 分割线：`#e5e7eb`，宽度 `1px`。
  - 选中态/浅灰背景：`#f9fafb`。
  - 正文主色：`#111827`。
  - 次级文字：`#4b5563` 或 `#6b7280`。
  - 弱提示文字：`#888888`。
  - 错误色：`#dc2626`。
- 圆角默认使用 `9px`；小菜单或代码块可使用 `4px` 到 `8px`，但同一区域要统一。
- 图标风格要一致：线性、无背景、灰色、线条略粗；同一工具栏内图标尺寸和描边一致。
- 顶部高频操作应轻量、低噪声；低频配置不要堆在首页，放入设置页。

## 布局规范

- 阅读型页面优先使用三栏布局：左导航/目录，中间内容，右辅助信息/大纲。
- 管理型页面优先使用左侧设置导航 + 右侧内容区。
- 左侧导航不要和右侧内容同时滚动；通常左侧固定或隐藏滚动，右侧内容独立滚动。
- 分栏分隔线使用 `1px` 灰线；需要拖拽时悬浮显示拖拽手柄。
- 分栏宽度要有最小和最大值，避免内容被挤压到不可用。
- 用户调整过的宽度应保存到 localStorage；双击分隔线恢复默认值。
- 顶部栏保持简洁：品牌、当前上下文、高频动作、全局入口。
- 文字过长时使用省略号，鼠标悬浮可通过 `title` 或 Tooltip 展示完整内容。

## 组件样式规范

- 下拉选择本体：无边框、无阴影、浅灰背景、圆角。
- 下拉弹层：纯白背景、圆角、轻微阴影；选中态使用浅灰背景，不要使用刺眼高亮。
- 搜索框：浅灰背景、圆角，左侧保留小搜索图标，文字颜色使用弱提示色。
- 搜索结果：只展示与检索相关的核心信息；关键词用主色高亮；内容命中展示前后摘要，过长用省略。
- 菜单：背景 `#f9fafb` 或白色，轻微阴影；打开后隐藏同组其他 hover 操作，避免穿透感。
- 树节点：文件夹和普通文件行高一致；层级缩进克制；文字垂直居中；超长省略。
- 箭头：展开向下，折叠向右；同一树内尺寸一致，不显示多余文件夹图标。
- 状态提示：loading、success、failed、empty 都要有清晰视觉反馈。
- 表单：错误提示紧贴字段或区域；异步加载下拉选项时显示灰色 loading。
- 导出、同步、索引等耗时操作不要只转按钮，要有可追踪状态区域或任务列表。

## 交互规范

- 页面加载、上下文切换和手动刷新都要有明确 loading 状态。
- 自动刷新只触发当前上下文，不影响其他用户或其他上下文。
- 失败状态必须可解释：按钮变红、tooltip 展示错误摘要、页面保留失败原因。
- 搜索框失焦后关闭搜索结果；搜索结果区域独立滚动，不触发整页滚动。
- 如果结果列表可继续滚动，底部可使用透明渐变提示还有更多内容。
- 更多菜单、弹层、编辑态在点击外部或窗口失焦时关闭；但点击弹层内部控件不能误关闭。
- 删除、退出登录、危险操作必须二次确认。
- 默认资源、内置管理员、关键系统配置等不可删除或必须明确禁用删除按钮。
- 新增列表项成功后，表单清空，新 item 可播放一次轻量进入动画。
- 同一列表内编辑态默认只允许一个 item 处于编辑中；编辑面板打开/关闭要有过渡动画。
- 路由跳转使用轻量滑入或淡入动画，避免页面突然闪烁。
- 任何按钮点击后必须有反馈：loading、toast、状态变更、下载开始或错误提示。

## 表单与配置规范

- 表单默认展示态和编辑态分离，列表 item 不应默认全是输入框。
- 远程选项不要要求用户手填；能从接口实时拉取的选项，应以下拉方式提供。
- 远程选项加载中显示 loading，拉取不到时显示空状态或明确错误。
- 保存失败时保留用户输入，不要清空表单。
- 新增成功后清空新增表单，编辑成功后退出编辑态。
- 配置页不要混入阅读页的高频操作；配置项按场景分组。
- 登出入口使用红色强调，并必须确认。

## 安全规范

- 所有文件路径必须做安全校验，禁止 `../`、绝对路径逃逸和越权读取。
- 文件下载、图片读取、导出结果只能访问当前授权资源范围。
- 私钥、密码、token、数据库 URL、内部服务器路径不得出现在前端响应、日志、错误 tooltip 或下载文件中。
- 外部命令和系统调用必须集中封装，入参白名单化，错误消息做脱敏。
- 管理接口必须加权限校验；普通接口也要校验登录态和资源可访问性。
- 环境变量提供 `.env.example`，真实值不入库。

## 部署规范

- Dockerfile 要考虑空目录、构建缓存、生产依赖、静态资源和 standalone 产物。
- Docker Compose 中服务名应稳定，内部访问通过服务名，外部访问通过 Nginx 端口。
- 数据目录、上传目录、导出目录、索引目录要持久化。
- 启动脚本要兼容 `docker compose` 和 `docker-compose`。
- 服务器网络不稳定时，应提供镜像源配置脚本或文档。
- 部署完成后至少验证：
  - 容器均为 running/healthy。
  - `/api/health` 可访问。
  - 首页能打开。
  - 登录、核心列表、核心详情、核心任务路径可用。

## 验证规范

- 代码修改后优先执行与改动范围匹配的最小验证：
  - 前端样式/交互：`npm run build -w frontend` + Playwright。
  - 后端逻辑/API：`npm run build -w backend` + 对应测试/API 调用。
  - 跨端联调：Docker Compose 启动 + 浏览器验证。
  - Dockerfile/脚本：实际 build 或 `bash -n`。
- Playwright 验证要覆盖真实操作：点击、输入、悬浮、失焦、拖拽、路由跳转、下载、接口错误提示。
- 验证失败时继续定位和修复；最终说明已验证命令、结果和剩余风险。

## 文档规范

- 需求、接口、UI、性能、部署、排查和决策要分文档沉淀。
- 接口文档必须同步菜单/页面动作和实际 API。
- UI 规范要说明颜色、圆角、布局、选中态、弹层、图标和动画，不只贴设计图。
- 性能文档要记录缓存 key、并发锁粒度、任务状态、索引策略和失效规则。
- 每次做出影响后续开发的结论，优先沉淀到项目级 `.codex/skills/04-内容创作与知识沉淀/01-上下文沉淀/project-context` 或 `docs/`。

## 默认完成标准

- 功能真实连后端，不用静态假数据冒充完成。
- UI 与设计规范一致，状态完整，失败可见。
- 接口契约、类型、错误处理和权限路径一致。
- 构建或测试通过；前端交互用 Playwright 验证。
- 部署脚本能在目标环境执行，失败时给出可行动错误信息。
