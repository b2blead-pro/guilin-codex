# 通用编码规范

## 适用场景

- 修改项目代码、脚本、配置、测试或工程文档。
- 做代码审查、重构、修 bug、补测试、整理工程规范。
- 用户要求“按我的编码规范”或整理项目工程规范时。

## 工作原则

- 先阅读相关代码、配置和现有文档，再做实现判断。
- 进入具体项目后，如果项目内存在 `.codex/skills`，按“一级用途分类 / 二级场景分类 / skill 名称”递归扫描目录，按需读取并优先遵循与当前任务相关的项目级 skill；旧项目仅在已经使用 `.codex/skill` 时兼容该单数目录。
- 实现前明确关键假设和成功标准；只有无法从上下文消除、且实质影响范围、外部行为、数据或发布目标的歧义才先向用户确认。其余沿用现有模式，必要时说明假设。
- 对复杂任务先给出简短计划，计划要包含每一步的验证方式。
- 尊重工作区已有改动，不覆盖、不回滚非本次产生的用户修改。
- 优先复用项目已有框架、工具函数、目录结构、命名和错误处理方式。
- 保持改动范围克制，只改与任务直接相关的文件。
- 不要顺手优化相邻代码、注释或格式；无关死代码可以指出，但不要删除。
- 简单优先，只写解决当前问题所需的最少代码，不加入预设扩展、临时灵活性或无需求支撑的配置项。
- 抽象只在能减少真实复杂度、复用明确、或符合项目既有模式时引入；短于 10 行的方法尽量不要封装，十几行以内且只有一个调用点的简单组装/转发方法也优先内联，避免为了“看起来整洁”拆出不方便阅读的私有方法。四行左右重复可以接受。如果你写了 200 行，但 50 行就够，就重写。
- 结构化数据优先使用解析器或项目已有 API，不用脆弱的字符串拼接处理。
- 调用 SDK、外部服务、系统能力或跨模块接口时，优先收敛到单一入口方法，并在入口内统一处理回调、错误、重试、并发保护和状态更新；业务流程只传入场景或参数，避免多个位置直接调用同一个 SDK 方法导致状态分散、可读性差和维护成本上升。
- 如果实现过程中判断逻辑快速膨胀、方法变长、相似代码大量重复或类职责过载，优先调整现有结构，不继续堆叠补丁。
- 参数超过 2 个且属于同一业务语义时，优先封装为对象；项目已有 builder 模式时沿用 builder。

## 代码质量

- 新增逻辑要覆盖异常、空值、边界条件和失败分支。
- 用户可见行为变更应同步更新测试、示例或文档。
- 日志、错误提示和注释保持简洁；修改或新增代码时，对关键变量和关键方法增加简明注释，避免解释显而易见的代码。
- 前端或 UI 改动要检查移动端和桌面端文本不溢出、元素不重叠、状态完整。
- 涉及运行时注入、脚本注入、调试注入或替换实现的代码，必须增加清晰标记；如果用户没有注入，APP 启动后要有显式提示。
- 数据库升级脚本默认接入 npm 启动命令，除非项目已有更明确的迁移入口。
- 新增 bash 脚本时，顶部增加简洁注释，说明作用和使用方法，并尽量保持兼容性。
- 新增或修改 Gradle 脚本时，需要为关键任务、兼容逻辑、跨模块注入、发布配置和非直观依赖关系增加简洁明了的注释，说明为什么需要这段逻辑。

## 验证规范

- 改完代码后，优先执行可行的构建、测试、lint 或运行验证。
- 验证命令选择与改动范围和风险匹配的最小集合；相关验证已通过后，只有新改动、失败或未解决的具体疑点才扩大或重复验证。
- 验证失败先归因，继续处理由本次改动引起或阻塞当前已授权目标的问题，包括用户已授权的前后端联动；对无关既有失败或无法推进的外部阻塞，说明失败命令、关键错误和剩余风险，不扩展修复范围或原样反复重试。
- 如果环境缺依赖、命令不可用或验证成本过高，最终回复中明确说明未验证原因。

## 沟通规范

- 一律使用中文回复，除非用户明确要求其他语言或代码内容必须使用英文。
- 编写、更新 skill 时使用中文，代码、命令、包名、类名等必须保留原文。
- 普通说明尽量避免小标题、表格和不必要的列表；代码审查、变更总结等需要可读结构时，可以使用必要的短列表。
- 避免“尽管面临诸多挑战”这类套路句式，避免“三重”“不是 X 而是 Y”这类刻意强调。
- 如果必须举例，把例子自然嵌入正文，不为了形式感展开长列表。

## GIT工具使用规范
- 除非用户明确要求，否则不要主动执行 `git push`、`git pull`、`git fetch`、`git merge`、`git rebase` 等会与远程仓库同步、拉取、合并或推送的操作；需要这些操作时先说明原因并等待用户确认。
- 如果推送代码到远程仓库而仓库不存在，可以使用 `git push --set-upstream origin <branch>`。
