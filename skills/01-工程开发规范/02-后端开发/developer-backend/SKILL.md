# 后端开发规范

当前仅包含后端异常处理规范。适用于本次任务涉及的后端代码；沿用项目既有的日志、全局异常处理和统一响应机制，不因应用本规范扩大为无关模块的整体重构。

## 后端异常处理规范

1. **禁止静默异常**：所有 `catch` 必须记录明确的错误日志，禁止空 `catch` 或仅打印简单文本。
2. **日志必须可定位**：异常日志至少包含业务场景、关键参数、异常原因及完整堆栈信息。关键参数涉及敏感信息时必须脱敏，禁止记录密钥等秘密信息。
3. **异常统一处理**：业务异常、系统异常统一通过全局异常处理机制转换，禁止随意向上抛出无语义异常。转换或包装异常时保留原始异常原因，确保日志能定位根因。
4. **错误信息统一透传**：异常最终应通过接口及网关返回明确的错误码和友好错误信息，使用户知道“发生了什么”，开发人员能够快速定位问题。网关透传或映射错误时，保留可追踪的错误码与请求标识，避免丢失错误语义。
5. **统一错误码体系**：建立统一的 `ErrorCode` / `ErrorCodeEnum`，集中维护错误码、错误描述及错误类型，禁止各模块随意定义错误码。已有统一错误码体系时复用并按需扩展。
6. **安全要求**：客户端返回信息不得暴露堆栈、SQL、服务器路径、密钥等敏感信息；详细异常仅记录在服务端日志中，服务端日志同样不得泄露密钥等秘密信息。对外错误信息使用安全、友好的描述，不直接返回原始异常文本。

## 推荐统一返回结构

`code + message + requestId/traceId + data`

- `code`：统一错误码体系中的错误码。
- `message`：安全、友好的错误描述。
- `requestId` / `traceId`：沿用项目选定的请求或链路标识字段，在客户端响应、网关与服务端日志之间保持可关联。
- `data`：业务数据；异常响应按项目既有约定返回空值或安全的必要内容。

确保一次异常能够通过 **错误码 + traceId → 网关 → 服务端日志** 完整追踪定位；项目使用 `requestId` 时遵循相同的关联要求。
