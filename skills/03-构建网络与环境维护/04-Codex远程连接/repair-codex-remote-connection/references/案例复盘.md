# Codex 远程连接与蜂窝代理案例复盘

## 现象

- Codex 普通对话可用，但手机 Remote 无法连接。
- 桌面端反复启用 Remote Control，仍显示失败。
- 蜂窝加速器已经打开，macOS 系统 HTTP、HTTPS、SOCKS 代理均指向 `127.0.0.1:7890`。

## 关键证据

1. Codex enrollment 已存在，`remote_control_enabled=1`，说明功能已启用，不是账号未登记。
2. `logs_2.sqlite` 持续出现：

   ```text
   timed out connecting to remote control websocket ... after 30s
   ```

3. 目标地址为：

   ```text
   wss://chatgpt.com/backend-api/wham/remote/control/server
   ```

4. 桌面内嵌 app-server 没有 `HTTP_PROXY`、`HTTPS_PROXY` 环境变量。
5. 直连 `chatgpt.com` 会超时，显式经过蜂窝代理的 HTTPS/WSS 探测能快速得到服务器响应。
6. 通过显式代理启动官方托管 daemon 后，日志立即变为 `Connected`，证明账号、节点和服务端均正常。

## 第一次修复为什么不完整

首次使用以下方式启动托管 daemon：

```bash
HTTP_PROXY=http://127.0.0.1:7890 \
HTTPS_PROXY=http://127.0.0.1:7890 \
codex remote-control start --json
```

daemon 成功连接，但桌面内嵌 app-server 仍没有代理，桌面设置页继续失败。两条进程随后复用同一登记，日志还出现：

```text
409 Conflict
Remote app server already online
```

这说明“另起一个能连接的 daemon”不能替代“修复桌面应用实际使用的进程”。

## 最终修复

1. 使用 `launchctl setenv` 写入大小写两套 `HTTP_PROXY`、`HTTPS_PROXY`，并设置本地 `NO_PROXY`。
2. 停止冲突的托管 daemon。
3. 完整退出 `/Applications/ChatGPT.app`，重新启动，让新桌面进程继承代理环境。
4. 对新 PID 重新读取环境和日志。

## 最终验证

- 新桌面 PID 包含正确的代理变量。
- 托管 daemon 未运行。
- 新进程启动后两秒内记录：

  ```text
  Disabled → Connecting → Connected
  connected to app-server remote control websocket
  ```

- 新进程远程模块只有 INFO，没有新的 WARN/ERROR。
- 新 PID 与 `127.0.0.1:7890` 存在多个 `ESTABLISHED` 连接。

## 可复用结论

- macOS 系统代理存在，不等于 Codex 的 Rust WebSocket 客户端一定会使用它。
- 必须检查真正承载桌面 Remote 的 app-server 进程环境。
- daemon 与桌面 app-server 是两条不同运行路径，不能把其中一条的成功当成另一条已修复。
- `409 Remote app server already online` 优先排查重复 app-server，不要先清认证或 enrollment。
- 停止命令超时不代表停止失败；必须以进程和 `codex doctor` 的实际状态为准。
- 修复完成必须验证新 PID、`Connected` 日志、零新增告警和代理套接字，不能只看 UI。
